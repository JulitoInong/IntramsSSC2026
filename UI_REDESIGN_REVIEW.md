# Front-end redesign and code review

## What changed
- Reworked `styles.css` and `student.css` only.
- Kept HTML structure, element IDs, JavaScript, SQL migrations, Supabase RPC names, attendance rules, and service-worker code unchanged.
- Introduced a cohesive navy / gold / emerald visual system, clearer hierarchy, improved spacing, touch-friendly controls, responsive layouts, and focus-visible states.
- Admin: refreshed statistics, session controls, roster rows, action toggles, status pills, and activity list.
- Student kiosk: clearer status, search results, selected-student panel, and large attendance actions.

## Major issues to verify (not changed because logic/backend changes were out of scope)

1. **Student page is not independently configured as a PWA.** `student.html` does not link `manifest.webmanifest`, and `student.js` does not register the service worker. The admin `app.js` registers the service worker, so installation/offline shell behavior may differ when a student opens `student.html` directly. Verify the desired install entry point and test from HTTPS.
2. **Service-worker cache version mismatch.** `service-worker.js` pre-caches CSS/JS with query versions that do not match the versions linked in `index.html` / `student.html`. Depending on browser cache behavior, users may see stale UI after an update. Bump cache names and keep precache URLs aligned during deployment.
3. **Two theme-color declarations in `index.html`.** The page declares `theme-color` twice with different values (`#111d3b` and `#17365d`). Browsers may select the later value; keep one consistent value.
4. **External runtime dependency.** Both pages load Supabase JS from jsDelivr. The service worker has CDN caching logic, but first load still needs network access to fetch the library. Test first-visit behavior and CDN failure handling.
5. **Public kiosk privacy.** Name search exposes matching students and their department/year to anyone who can open the kiosk. Keep kiosks supervised and show only the minimum data needed to distinguish matches.
6. **Admin destructive control.** `Deactivate all students` is prominent and potentially high-impact. Verify its confirmation/authorization safeguards and consider a stronger confirmation flow before real deployment.
7. **Offline behavior is not equivalent on both pages.** The admin has local cache/queue code; `student.js` uses public RPCs and has no matching local attendance queue. Do not assume student check-in can record offline just because the admin portal has offline-related features.

## Verification
- The archive structure and original front-end files were read before editing.
- No JavaScript, SQL, schema, or attendance logic was edited.
- Visual layout still depends on the current DOM and dynamic classes generated by the original JavaScript. Run the app over HTTPS and verify both pages at desktop, tablet, and phone widths before replacing the working deployment.
